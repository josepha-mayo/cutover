# Controlled detection ablation — not a customer benchmark

The project needs a measurable claim that survives review. On the **three deliberately unsafe rollout patterns** shipped with Cutover, the new-version baseline detects **0/3**, completed-rollout checks detect **2/3**, and adding migration-statement windows detects **3/3**. This exact result repeats on the Parcel and Relay sample contracts. The two contracts have the same structural rename problem, so this is one curated defect set under two names and seeds, not six independent incidents.

| Stage | Direct rename | One-time backfill | Late bridge | Unsafe patterns detected |
| --- | --- | --- | --- | --- |
| New-version baseline only | Passes 8/8 | Passes 8/8 | Passes 8/8 | 0/3 |
| Completed-rollout schedules | Fails 60/76 | Fails 48/76 | Passes 76/76 | 2/3 |
| Add migration-statement windows | Fails 8/16 windows | Fails 8/24 windows | Fails 16/48 windows | 3/3 |

The late bridge is the incremental finding. It looks safe after the migration finishes, yet a write can arrive after backfill and before synchronization. The 16 failures include old updates and inserts across multiple statement boundaries. The window-safe reference passes 76/76 completed-rollout and 48/48 window probes in each sample. Removing any one of its synchronization triggers causes failures in the existing negative controls.

The additional prewritten cross-record trap probes a different blind spot and is excluded from the three-pattern table above. It begins with the window-safe bridge, then resets the first seeded record when the second is written. It passes all 8 same-version baseline checks and all 56 migration-window probes, but is blocked at 100/132 overall in both bundled contracts. Its shortest witness shows writes to IDs 101 then 102, followed by the old reader observing the first record's original value instead of its acknowledged update. This is a synthetic adversarial fixture, not an independent field incident.

Reproduce the table with `python -m evidence.build_ablation`; its output is [`evidence/ablation.json`](../evidence/ablation.json). Each candidate runs against a fresh SQLite database with separate migration, old-worker, and new-worker connections and a fixed old adapter and an independent ledger of acknowledged writes. Version 0.3.13 requires the new reader to read the target without accessing the old column, new updates and inserts to carry their values into the target on a trigger-free snapshot, and the target column to preserve ledger values. Its schema and access checks follow SQLite's case-insensitive identifier semantics for imported contracts. It rotates two-write targets across schedules and payloads, covering every ordered pair of up to 16 seeded records somewhere in a passing full suite. This catches nonadjacent cross-record corruption that the earlier directed ring missed. The evaluator also rejects old-adapter no-ops, a reader that only touches the target in a no-op expression, an updater that self-assigns the target, and a new insert that writes only the old field. Explicit dual-writes remain valid. Connection-local `TEMP` objects are denied: replacing the persistent synchronization triggers with temporary ones falsely passed 124/124 before this correction because every probe used one connection. The JSON includes plan, contract, suite and engine hashes. The selected fixtures and input strings define the scope; these numbers are not a general accuracy, incident-reduction, or time-savings estimate.

The pre-event Codex baseline supports a third, user-supplied warehouse fixture through the CLI, browser, and Bob MCP tool, and can write a Markdown review from the executed JSON report. That fixture has the same structural rename problem; it does not increase the independent-incident count or turn this ablation into a general accuracy claim. Version 0.3.13 additionally rejects virtual-table creation and removal, which fall outside the bounded ordinary-table contract; this hardening does not change the controlled ablation counts. The subsequent event-period Bob repair and original PR review gate have [actual task histories and independently replayed outcomes](PROVENANCE.md). Those results are separate from this pre-event ablation. No productivity gain is established without a measured comparison or a real engineer's feedback.
